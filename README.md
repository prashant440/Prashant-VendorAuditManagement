# Vendor Audit Management (AI-assisted)

Built for the Gerald pre-interview coding challenge. Auditors track vendors and
findings; an AI assist endpoint summarizes a vendor's findings and returns an
explainable Low/Medium/High risk rating.

## Stack & why

- **Backend:** C# / .NET 8 minimal API + EF Core (Code First) + **SQL Server**.
  `IVendorRepository` is the only interface the endpoints/services depend on;
  `AppDbContext` and `Program.cs` are the only two files that know the
  provider is SQL Server, via `UseSqlServer(...)` and a connection string in
  config — nothing else in the app cares.
- **Frontend:** React (Vite), plain `fetch`, no state library — the app is
  two screens, a state library would be overhead.
- **AI:** behind an `IAiAssistService` interface with two implementations:
  - `StubAiAssistService` (default, no key needed) — deterministic, still
    grounded in real finding data.
  - `AnthropicAiAssistService` — calls the Anthropic API for the narrative
    summary, but the **risk rating itself always comes from the deterministic
    `RiskScoringService`**, never from the model. See "AI grounding" below.

## Database setup (SQL Server)

You need a reachable SQL Server instance. Two options:

**Option A — Docker (Linux/Mac/Windows, easiest):**
```bash
docker compose up -d
# wait ~15s for SQL Server to finish starting
```
This starts SQL Server 2022 on `localhost:1433` with `sa` / `YourStrong!Passw0rd`
— matching the default connection string in `appsettings.json` already, so no
further config is needed.

**Option B — SQL Server LocalDB (Windows only):**
Copy `backend/VendorAudit.Api/appsettings.Development.json.example` to
`appsettings.Development.json` in the same folder — it points at
`(localdb)\mssqllocaldb`, which ASP.NET Core config automatically overlays
onto `appsettings.json` in the Development environment.

**Then create the schema (once, from the API project folder):**
```bash
cd backend/VendorAudit.Api
dotnet tool install --global dotnet-ef   # first time only
dotnet ef migrations add InitialCreate
```
This generates `Data/Migrations/*`. `Program.cs` calls
`db.Database.Migrate()` on startup, which creates `VendorAuditDb` and applies
the migration automatically the first time you run the API — you don't need
to run `dotnet ef database update` separately, though you can to apply it
without starting the app.

## How to run

**Backend** (needs .NET 8 SDK + SQL Server reachable, see above):
```bash
cd backend/VendorAudit.Api
dotnet restore
dotnet run
```
Runs on `http://localhost:5000`, applies migrations and seeds 5 vendors into
`VendorAuditDb` on first run, Swagger UI at `/swagger` in dev.

**Frontend** (needs Node 18+):
```bash
cd frontend
npm install
npm run dev
```
Runs on `http://localhost:5173`, points at `http://localhost:5000/api`.

**Enabling the live LLM (optional):** set an environment variable before
`dotnet run`:
```bash
export Anthropic__ApiKey=sk-ant-...
```
With no key set, the app automatically falls back to the deterministic stub
— nothing else changes, including the API response shape.

## What's built

- `Vendor` / `Finding` data model (severity, status, notes, date) via EF Core
  Code First, with a SQL Server migration (`Data/Migrations/InitialCreate`,
  generated by `dotnet ef migrations add`).
- 5 seeded vendors with 1–3 findings each (`Data/DbSeeder.cs`), covering a
  spread of severities and statuses so the risk ratings differ meaningfully.
- `GET /api/vendors` — list view with open-finding count and highest open
  severity per vendor.
- `GET /api/vendors/{id}` — detail view with all findings.
- `POST /api/vendors/{id}/findings` — add a finding.
- `POST /api/vendors/{id}/ai-assist` — the AI feature: summary + risk rating
  + reasoning grounded in that vendor's findings.
- React list → detail → "Generate AI Risk Summary" flow.

## AI grounding — the main design decision

The risk rating is **not** something the LLM decides. `RiskScoringService` is
a pure, deterministic function: severity weight (Critical=8, High=5,
Medium=2, Low=1) × status multiplier (Open=1.0, InRemediation=0.6,
Accepted=0.3, Resolved=0.1), summed per vendor, thresholded into
Low/Medium/High. It's unit-testable and an auditor can reproduce the number
by hand from the findings table.

The LLM (when enabled) is only ever asked to narrate that already-computed
result and cite specific finding titles — it's explicitly instructed not to
propose a different rating and not to reference findings outside the list it
was given. This means the AI output can never silently invent a risk level
that doesn't trace back to recorded data, which is what "grounded" means for
an audit tool.

## Auth, auditability, production data protection

Not implemented in the 2-hour scope — notes on what a real version needs:

- **Auth:** the API has none right now. Production would need
  auth (Azure AD / OIDC) with roles at minimum for `Auditor` (read/write
  findings) vs `Viewer` (read-only) vs `Admin` (manage vendors), enforced
  with `[Authorize]` policies per endpoint group.
- **Auditability:** findings currently have no "who/when changed" trail.
  A real system needs an append-only audit log table (actor, timestamp,
  before/after) for every finding mutation and every AI-assist call
  (including the exact prompt and model version used), since audit findings
  are themselves subject to audit.
- **Production data protection:** no real vendor/customer data was used —
  all seed data is fictional (`*.example` emails). In production: encrypt
  the connection string and any LLM API key via a secrets manager (Azure Key
  Vault), never log finding `Notes` verbatim (they may contain PII), and
  scope the LLM call to only the fields it needs rather than the whole
  vendor object.
